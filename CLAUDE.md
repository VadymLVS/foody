# PantrySync — как здесь работать

Этот файл читается автоматически в начале сессии. Он задаёт правила работы и
описывает состояние сборки. Если правила и код расходятся — прав этот файл.

## Кто и что

Заказчик и единственный проверяющий — **Vadym**. Приложение семейное: им
пользуются двое — Vadym и **Алина** (не Арина). Тестирование идёт только на
iPhone 16 Pro Max: PWA с домашнего экрана и в Safari.

Терминала у Vadym нет. Он работает через веб-интерфейс GitHub, Vercel и
Supabase. Значит: любая выдача — это либо коммит в репозиторий, либо архив с
точными указаниями, какие файлы залить. Никогда не отправлять его «выполнить
команду» и не ссылаться на локальный запуск.

- Репозиторий: `VadymLVS/foody`
- Прод: **foody-five-lemon.vercel.app** (постоянный адрес; на телефоне закреплён он)
- Supabase: проект `qhvjyxexfnkhdzwbtfmw`
- Переменные Vercel: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` — тип Config,
  окружения Production и Preview

## Порядок работы (правила Vadym)

1. **Фидбек не означает «правь код».** Замечание записывается в бэклог с
   разбором причины и открытыми вопросами. Код трогается только после команды
   «вносим», «апдейтим» или «собирай».
2. **Визуальные решения — сначала макетом.** Иконки, цвета, размеры, композиция:
   показать варианты, дождаться выбора, только потом собирать. «Давай с …» внутри
   обсуждения макета — это правка макета, а не команда собирать. Однажды за
   нарушение этого правила прилетело прямо: «Больше не делай так».
3. **Перед реализацией — уточняющие вопросы.** Лучше четыре вопроса списком, чем
   догадки. Если Vadym говорит «сделай максимально удобно» — решать самому, но
   записать каждое решение с обоснованием.
4. **Выдача целиком, инструкции в чате.** Файлы отдавать полностью, шаги писать
   в сообщении. Не отправлять искать что-то самому.
5. **Порядок деплоя всегда один:** сначала SQL миграции в Supabase, потом код.
6. **Заливка файлов не удаляет.** Если версия что-то удаляет, назвать эти файлы
   отдельно — их Vadym удаляет вручную.

## Безопасность — не обсуждается

- В клиент идёт только publishable-ключ `sb_publishable_…`
- Secret-ключ `sb_secret_…` не использовать нигде: он обходит RLS
- `ANTHROPIC_API_KEY` — только в секретах Edge Function Supabase, никогда в клиенте
- Пароли и токены не просить присылать в переписку: они останутся в истории
  навсегда. Автоматизация — через секреты GitHub Actions

## Проверка перед выдачей

```bash
npm run typecheck        # tsc --noEmit
npm run lint             # eslint .
npm test                 # 41 модульный тест: питание, поиск, группировка, очередь
npm run build            # сборка; предупреждения о размере чанка быть не должно
```

Сценарии в браузере (Playwright, python) живут вне репозитория, в рабочей папке
сессии. Против собранной версии: `npm run build && npx vite preview --port 4173`.
На момент v0.17.1 их 170 в шести наборах. Никогда не убивать превью через
`pkill -f "vite preview"` — это убивает и собственную оболочку.

Права и данные проверяются на локальном Postgres с заглушкой `auth.uid()`:
49 проверок по миграциям 0008 и 0009. Скрипты — в рабочей папке сессии.

## Чего в коде нет намеренно

- Типы базы не сгенерированы: `createClient` без генерика `Database`. Сгенерировать
  можно только против живого проекта — `npm run db:types`, запускает Vadym.
- Слой переключения языков убран: словарь один, но строки всё равно идут через
  `t()` — добавить язык значит положить рядом второй словарь (Q-4 не решён).
- Полноценного офлайна нет: читать без сети приложение не умеет, но записи не
  теряются — их держит очередь `src/shared/lib/opQueue.ts`.
