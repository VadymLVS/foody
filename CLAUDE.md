# PantrySync — как здесь работать

Этот файл читается автоматически в начале сессии. Он задаёт правила работы и
описывает состояние сборки. Если правила и код расходятся — прав этот файл.

## Кто и что

Заказчик и единственный проверяющий — **Vadym**. Приложение семейное: им
пользуются двое — Vadym и **Алина** (не Арина). Тестирование идёт только на
iPhone 16 Pro Max: PWA с домашнего экрана и в Safari.

Терминала у Vadym нет. Он работает через веб-интерфейс GitHub, Vercel и
Supabase. Значит: любая выдача — это либо коммит в репозиторий, либо архив с
точными указаниями, какие файлы залить. Никогда не отправлять его «выполнить
команду» и не ссылаться на локальный запуск.

- Репозиторий: `VadymLVS/foody`
- Прод: **foody-five-lemon.vercel.app** (постоянный адрес; на телефоне закреплён он)
- Supabase: проект `qhvjyxexfnkhdzwbtfmw`
- Переменные Vercel: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` — тип Config,
  окружения Production и Preview

## Порядок работы (правила Vadym)

1. **Фидбек не означает «правь код».** Замечание записывается в бэклог с
   разбором причины и открытыми вопросами. Код трогается только после команды
   «вносим», «апдейтим» или «собирай». За нарушение прилетало прямо: «Больше не
   делай сразу правку по комментарию, если не говорил это делать. Мне нужно
   внести в твоё решение изменения, а ты уже проделал кучу работы, которую
   сейчас нужно править.» То есть после замечания обычно идёт правка самого
   решения — сначала разбор и вопросы, сборка по команде.

   **Исключение сформулировано заново (10-01), прежняя формулировка оказалась
   дырявой.** Было: «моя поломка, которая мешает работать, чинится сразу». Это
   оставляло решение за мной, а я в таком случае заинтересованная сторона:
   поломка моя, и «мешает работать» я истолкую в свою пользу. Так и вышло
   с v0.18.1 — я собрал билд, хотя в том же сообщении сам дал обходной путь
   в одно нажатие, то есть сам показал, что ничего не заблокировано. Цена:
   лишняя заливка руками при четырёх открытых пунктах по тем же файлам.

   Теперь исключение требует **двух** условий сразу, и оба проверяемые:
   1. обходного пути нет вообще — не «неудобно», а никак;
   2. в исправлении нет ни одного решения, только возврат к согласованному.

   Не выполнено хотя бы одно — называю причину, даю обходной путь, пишу
   в бэклог, жду команду. И по умолчанию билды копятся: один деплой на пакет
   правок, а не один на находку. Заливка через веб-интерфейс — самая дорогая
   часть работы у Vadym, правило существует ради неё.

   Отдельно: «исправление бага» — не безопасная категория. В нём тоже бывают
   решения (в том же v0.18.1 я сам выбрал сбрасывать вкладку на «Все», хотя
   можно было иначе), и такие решения спрашиваются, как любые другие.
2. **Визуальные решения — сначала макетом.** Иконки, цвета, размеры, композиция:
   показать варианты, дождаться выбора, только потом собирать. «Давай с …» внутри
   обсуждения макета — это правка макета, а не команда собирать. Однажды за
   нарушение этого правила прилетело прямо: «Больше не делай так».
3. **Перед реализацией — уточняющие вопросы.** Лучше четыре вопроса списком, чем
   догадки. Если Vadym говорит «сделай максимально удобно» — решать самому, но
   записать каждое решение с обоснованием.
4. **Выдача целиком, инструкции в чате.** Файлы отдавать полностью, шаги писать
   в сообщении. Не отправлять искать что-то самому.
5. **Порядок деплоя всегда один:** сначала SQL миграции в Supabase, потом код.
6. **Заливка файлов не удаляет.** Если версия что-то удаляет, назвать эти файлы
   отдельно — их Vadym удаляет вручную.

## Состояние на 2026-10-04 (v0.21)

Выдано и проверено: пакеты 1–3 предрелизного обзора, пункты бэклога 37–57.
Открытых пунктов нет. Миграции 0008–0011; v0.20 и v0.21 новых не добавляют.

**Экран «Блюда» — каталог** (D-106): блюда кухни и весь справочник по питанию,
по алфавиту. Блюдо справочника — виртуальное (`lib:<ключ>`), в базу пишется
только при выборе (`useAddLibraryToMenu`, нажатия в очереди). «Отмена» выбора
убирает такие блюда вместе с продуктами. В тестах не нажимать «первую плитку»:
первые по алфавиту — блюда справочника; блюдо кухни выбирать по имени.

**Справочник блюд — 113 блюд, мясных не больше 10 %** (D-104, условие Vadym).
Он живёт в четырёх местах: `dishLibrary.ts` (состав и единицы продуктов),
словарь `ru.ts` (названия блюд и продуктов), `dishRecipes.ts` (рецепты),
`diet.ts` (группы питания). Добавляя блюдо, править все четыре;
`dishLibrary.test.ts` поймает пропуск и превышение доли мясных.

Что сделано крупным: приглашения закрыты правами и триггером, чужое блюдо не
принимается в меню, `plan_needs` не удваивает количества, почта соседей по кухне
не отдаётся, все миграции идемпотентны, модалки с прокруткой и учётом клавиатуры,
свой шрифт и иконки PWA, доставка обновлений тостом, списки покупок (постоянные
и разовый «купить сейчас») со сборкой по всей кухне и заявками по количеству,
разделённая сборка, модульные тесты.

Четыре вещи, которые легко нарушить обратно:
- **«Куплено» — своя отметка позиции, не наличие дома** (D-098). Прогресс
  считается по `bought`. Отметка ставит наличие, снятие возвращает
  `stock_before`, количество продукта при снятии НЕ обнуляется.
- **Вкладка отдела внутри списка не применяется** (D-102). Фильтр списка идёт
  раньше вкладки, иначе список выглядит пустым.
- **Лаймовая грань слева значит только «нужно для блюда»** (D-097). Внутри списка
  покупок её нет, даже если у позиции есть заявка.
- **Заявка списка живёт только в списке** (D-093). `product_list_items.quantity`
  никогда не пишется в `products.quantity`: первое — «сколько взять», второе —
  «сколько лежит дома».

Правила по интерфейсу, выведенные из замечаний:
- **Свой орган управления не придумывается, если такой уже есть** (D-095).
  Панель количества в строке продукта одна на все экраны; в сборке списка
  у неё меняется только подпись.
- **Скрытый жест работает только как дубль видимого пути** (D-100). Свайп или
  долгое нажатие как единственный путь к редкому действию не годится.
- **Значок нужен там, где заменяет слово, а не добавляется к нему** (D-099).
- **У экрана, где человек делает работу, должен быть видимый конец** (D-101).
  «Сохраняется сразу» годится для правки одного числа, не для экрана целиком.
- **Переключатель раскрывается от себя** (D-099). Лист снизу — для списков
  действий; выбор из нескольких открывается дропдауном от нажатого элемента.

Проверять на iPhone (браузером не воспроизводится): нажатие подсказки продукта
с открытой клавиатурой, иконка на домашнем экране, кнопка «Сохранить» в длинной
форме при открытой клавиатуре, полоса разового списка, компактный выбор единицы
в строке состава — он пока 12 px и может увеличивать страницу при фокусе.

Урок из тестов 09-30: половина находок с телефона — это то, что в браузере
выглядит нормально. Прокрутка пальцем, увеличение страницы при фокусе, элементы
под клавиатурой и под кнопками формы проверяются только на устройстве.

Второй урок того же дня, уже про код: **результат запроса не ставится в
зависимости эффекта, наполняющего форму** (D-092). Список продуктов получает новую
ссылку при каждом обновлении — при создании продукта из той же формы, при отметке
другого человека через realtime — и форма обнуляется под руками. Наполнять форму
ровно один раз на открытие, состав хранить идентификаторами.

И третий: регрессионный тест обязан падать на прежнем коде. Прежде чем поверить
в исправление, я возвращаю поломку на место и убеждаюсь, что набор её ловит.

Урок 10-01 про интерфейс: **скрытый жест работает только как дубль видимого
пути.** В п. 11 долгое нажатие по строке продукта никто не находил, и мы вывели
«⋯» в панель. Через две недели я предложил свайп по строке дропдауна как
единственный путь к правке — тот же промах. Если действие редкое и о нём не
знают, оно обязано быть видимым.

И про украшения: значок нужен там, где он **заменяет** слово, а не добавляется
к нему. В дропдауне списков я поставил иконку каждому виду, хотя вид уже сказан
текстом и числом позиций — Vadym это снял одной фразой «не нужно никаких иконок,
это просто список».

## Безопасность — не обсуждается

- В клиент идёт только publishable-ключ `sb_publishable_…`
- Secret-ключ `sb_secret_…` не использовать нигде: он обходит RLS
- `ANTHROPIC_API_KEY` — только в секретах Edge Function Supabase, никогда в клиенте
- Пароли и токены не просить присылать в переписку: они останутся в истории
  навсегда. Автоматизация — через секреты GitHub Actions

## Проверка перед выдачей

```bash
npm run typecheck        # tsc --noEmit
npm run lint             # eslint .
npm test                 # 69 модульных тестов: каталог и справочник блюд, питание, поиск, очередь
npm run build            # сборка; предупреждения о размере чанка быть не должно
```

Сценарии в браузере (Playwright, python) живут вне репозитория, в рабочей папке
сессии. Против собранной версии: `npm run build && npx vite preview --port 4173`.
На момент v0.21 их 348 в тринадцати наборах. Регистрация с подтверждением
почты проверяется против отдельной сборки с подменённым Supabase
(`VITE_SUPABASE_URL=https://fakeproject.supabase.co`), запросы к `/auth/v1`
перехватываются в Playwright. Никогда не убивать превью через
`pkill -f "vite preview"` — это убивает и собственную оболочку.

Права и данные проверяются на локальном Postgres с заглушкой `auth.uid()`:
63 проверки по миграциям 0009–0011 (плюс 49 по 0008 и 0009 ранее). Скрипты — в рабочей папке сессии.

## Чего в коде нет намеренно

- Типы базы не сгенерированы: `createClient` без генерика `Database`. Сгенерировать
  можно только против живого проекта — `npm run db:types`, запускает Vadym.
- Слой переключения языков убран: словарь один, но строки всё равно идут через
  `t()` — добавить язык значит положить рядом второй словарь (Q-4 не решён).
- Полноценного офлайна нет: читать без сети приложение не умеет, но записи не
  теряются — их держит очередь `src/shared/lib/opQueue.ts`.
