## Продукт и дистрибуция

### D-001 · 2026-07-28 · Принято
**Дистрибуция: сначала PWA, App Store — только после появления нативной ценности.**

Контекст: приложение в текущем виде — список, тогглы, модалки. Всё это работает в браузере.
App Store Guideline 4.2 отсеивает «переупакованные сайты»; отказ стоит не только времени, но и замедления всех последующих ревью.

Решение:
1. **Этап 1** — PWA на Vercel. Установка на домашний экран, share-ссылки для семьи.
2. **Этап 2** — упаковка в Capacitor, когда появится хотя бы одна функция, невозможная в браузере (сканирование чека камерой — главный кандидат).
3. Android/Google Play проще и может быть сделан раньше iOS.

Последствия: архитектура с первого дня пишется как Capacitor-ready. Все решения ниже вытекают из этого.

---

### D-002 · 2026-07-28 · Принято
**Отказ от Next.js Server Actions. Клиент ходит в Supabase напрямую.**

Контекст: внутри Capacitor фронтенд грузится с `capacitor://localhost` как статические файлы — Node-рантайма рядом нет, Server Actions не выполнятся.

Решение: весь доступ к данным — через `@supabase/supabase-js` с клиента. Защита — RLS в базе, а не серверный слой. Операции, которые клиент не может выполнить безопасно (вступление в кухню по коду, создание кухни, удаление аккаунта), выносятся в Postgres-функции `SECURITY DEFINER`.

Последствия: сборка одна и та же для веба и для нативной обёртки. Раздел «API / Server Actions» из старой спеки удалён целиком.

---

### D-003 · 2026-07-28 · Принято
**Стек: Vite + React + React Router. Next.js не используем.**

Контекст: после D-002 из Next.js не используется ничего — ни SSR, ни ISR, ни серверные метаданные. Остаётся только оверхед и конфликты с `output: 'export'`.

Решение: Vite 5 + React 18 + React Router v6. Быстрее сборка, проще Capacitor, меньше магии, статический вывод по умолчанию.

Последствия: одна и та же сборка едет на Vercel и в Capacitor. Никаких серверных маршрутов в проекте нет и не появится — если что-то нельзя сделать на клиенте, это Postgres-функция, а не эндпоинт.

---

### D-004 · 2026-07-28 · Принято (пересмотрено в тот же день)
**Swipe-режим выбора блюд входит в MVP-1 как основная функция.**

Контекст: изначальная мотивация продукта — облегчить ежедневный выбор «что есть». Учёт продуктов — фундамент, свайпы — то, ради чего всё затевалось. Первоначально был отложен в MVP-2; решение пересмотрено: без свайпов продукт неотличим от десятка списков покупок.

Решение: MVP-1 = продукты + блюда + **свайп-режим и план дня** + реалтайм + share. Таблица `meal_plans` активна с первого релиза. Спека режима — раздел 4 в `02-product-specification.md`.

Последствия:
- Порядок разработки: продукты → блюда → свайпы. Свайпы не могут работать без первых двух.
- Появляется третье измерение состояния — «сегодняшний план», он локален для пользователя, а не общий для кухни (см. D-019).
- Характер приложения (реакции на отказы) становится частью MVP и требует отдельного банка фраз.

---

### D-019 · 2026-07-28 · Принято
**План дня — персональный, не общий для кухни.**

Контекст: кухня общая, но «что я хочу съесть сегодня» — личное. Если план общий, два человека будут перетирать выбор друг друга.

Решение: `meal_plans` содержит `user_id`. Каждый свайпает своё. На экране плана видно, что выбрали остальные («Арина выбрала борщ») — но перезаписать чужой выбор нельзя.

Последствия: список покупок по плану собирается из объединения планов всех участников на дату.

---

### D-020 · 2026-07-28 · Принято
**Колода свайпов — не случайная. Приоритет: что можно приготовить прямо сейчас.**

Контекст: смысл продукта в том, чтобы не заставлять человека думать. Показывать блюдо, для которого нет половины ингредиентов, — это добавлять решение, а не убирать.

Решение: порядок колоды —
1. Блюда, готовые полностью (`missingCount = 0`) — перемешаны случайно;
2. Блюда, где не хватает 1–2 ингредиентов — с пометкой «нужно докупить: молоко»;
3. Остальные не показываются вообще.

Внутри первой группы — дополнительный сдвиг: блюда, которые давно не выбирались, идут раньше. Иначе колода вырождается в одни и те же три позиции.

---

### D-021 · 2026-07-28 · Принято
**Реакции на серию отказов — банк фраз, без повторов, с нарастанием.**

Контекст: задуманная «личность» приложения. Легко скатиться в раздражающее.

Решение: фразы показываются на 5-м, 10-м, 15-м и 20-м свайпе влево подряд. Тон нарастает от нейтрально-шутливого к абсурдному. Счётчик сбрасывается при любом свайпе вправо. Фраза не повторяется, пока не исчерпан весь банк. **Отключается в настройках** — не всем это смешно, и на третий день может раздражать.

## Данные и логика

### D-005 · 2026-07-28 · Принято
**Ингредиент блюда ссылается на `product_id` + хранит `product_name` как снапшот.**

Контекст: в старой спеке ингредиент — только строка. Переименовал «Молоко» → «Молоко 3.2%» — блюдо потеряло связь. Сравнение шло через `toLowerCase()`, то есть «Помидоры» ≠ «помидор».

Решение: `product_id uuid references products(id) on delete set null` + `product_name text not null` (снимок на момент добавления). Готовность блюда считается по `product_id`; `product_name` используется для отображения, если продукт удалён.

---

### D-006 · 2026-07-28 · Принято
**`in_stock` — единственный источник правды. `quantity` при выключении не сбрасывается.**

Контекст: старая спека сбрасывала количество в 0 при переключении в OFF. Случайный тап — и данные потеряны.

Решение: `quantity` сохраняется всегда. При `in_stock = false` количество просто не показывается в UI. Комбинация «в наличии, количество 0» допустима и означает «есть, сколько — не считали».

---

### D-007 · 2026-07-28 · Принято
**Сортировка списка: категория → название. Не алфавит по всему списку.**

Контекст: в старой спеке компаратор был сломан (второе сравнение недостижимо). Но главное — в магазине ходят по отделам, а не по алфавиту.

Решение: группировка по категориям со sticky-заголовками, внутри категории — алфавит. Порядок категорий фиксированный (Овощи → Фрукты → Молочка → Мясо → Бакалея → Заморозка → Напитки → Бытовое → Прочее), а не алфавитный.

---

### D-008 · 2026-07-28 · Принято
**Поиск: подстрока с приоритетом префикса, порог 2 символа, нормализация.**

Контекст: `startsWith` не находит «Хлеб бородинский» по запросу «бородин», а порог в 3 символа ломает поиск «яйцо» → «яй».

Решение: нормализация (lowercase, ё→е, схлопывание пробелов), фильтр `includes`, сортировка результатов: сначала совпадения с начала, потом остальные. Порог — 2 символа. Всё на клиенте (список продуктов кухни редко превышает 200 записей).

---

### D-009 · 2026-07-28 · Принято
**Удаление продукта — через toast «Отменить», без модалки подтверждения.**

Решение: продукт помечается `deleted_at` (soft delete), из UI исчезает мгновенно, 5 секунд висит toast с «Отменить». Физическое удаление — фоновой чисткой раз в 30 дней.
Модалка подтверждения остаётся только для необратимых действий: удаление кухни, удаление участника, удаление аккаунта.

---

### D-010 · 2026-07-28 · Принято
**Реалтайм: подавление собственного эха.**

Контекст: оптимистичное переключение тоггла + прилетевшее обратно собственное событие = мигание.

Решение: в `products` добавлено поле `updated_by`. Клиент игнорирует входящие события, где `updated_by = собственный user_id` **и** для этой записи есть незакрытая локальная операция. Плюс локальный `pendingOps: Map<id, {value, ts}>` с таймаутом 5 сек на случай потери ответа.

---

### D-011 · 2026-07-28 · Принято
**Инвайт-ссылка: срок жизни, отзыв, отдельный код для отзыва.**

Контекст: UUID не угадать перебором, но ссылка живёт вечно и утекает в семейных чатах, скриншотах, буфере обмена.

Решение: `invite_code` + `invite_expires_at` (по умолчанию +7 дней). Владелец может сгенерировать новую (старая мгновенно перестаёт работать) или отключить приглашения совсем. Вступление — только через RPC с проверкой срока.

## Интерфейс

### D-012 · 2026-07-28 · Принято
**Эмодзи убраны из интерфейса. Иконки — `lucide-react`.**

Контекст: 🛒🍽️⚙️✅❌ как элементы UI выглядят несерьёзно, по-разному рендерятся на платформах и не проходят по Apple HIG.
Решение: SVG-иконки, единый размер 20/24px, цвет через `currentColor`. Эмодзи допустимы только в текстах пустых состояний.

### D-013 · 2026-07-28 · Принято
**Голосовой ввод спрятан за абстракцией `VoiceInput`.**

Контекст: Apple не включила Web Speech API в WKWebView, при этом `webkitSpeechRecognition` в `window` присутствует — проверка на существование даёт ложноположительный результат, распознавание молча не работает.
Решение: интерфейс с двумя реализациями — Web Speech API (браузер) и `@capacitor-community/speech-recognition` (нативная сборка). Определение платформы, а не feature-detection. Кнопка микрофона скрывается, если ни одна реализация недоступна.

### D-014 · 2026-07-28 · Принято
**Тач-таргеты минимум 44×44px, safe-area insets с первого дня.**
Иконка «⋮» в карточке — визуально 20px, кликабельная зона 44px. Нижняя навигация — `padding-bottom: env(safe-area-inset-bottom)`.

## Безопасность

### D-015 · 2026-07-28 · Принято
**RLS через `SECURITY DEFINER`-функцию `is_kitchen_member()`.**

Контекст: политика на `kitchen_members`, которая проверяет членство через саму `kitchen_members`, вызывает бесконечную рекурсию в Postgres — классическая ошибка Supabase-проектов.
Решение: вспомогательная функция `is_kitchen_member(uuid)` с `security definer` и зафиксированным `search_path`. Все политики ссылаются на неё.

### D-016 · 2026-07-28 · Принято
**Каждая политика имеет и `using`, и `with check`.**

Контекст: в старой спеке `for all using (...)` без `with check` — любой авторизованный пользователь мог вставить строку в чужую кухню.
Решение: политики разделены по операциям (`select` / `insert` / `update` / `delete`), у пишущих обязателен `with check`. Проверка внесена в чеклист ревью.

### D-017 · 2026-07-28 · Принято
**Фото блюд: приватный бакет, EXIF стрипается на клиенте.**
Фотография кухни содержит GPS-координаты дома. Перед загрузкой изображение перерисовывается через canvas — метаданные теряются, заодно сжимается размер. Бакет не публичный, доступ — по подписанным URL, политики на `storage.objects` по `kitchen_id` в пути.

### D-018 · 2026-07-28 · Принято
**Удаление аккаунта — обязательная функция с первого релиза.**
App Store Guideline 5.1.1(v) требует удаление аккаунта внутри приложения. Реализуется как RPC с передачей владения кухнями или их удалением. Делаем сразу, чтобы не встраивать задним числом.

## Визуальный язык и модель (сессия 2)

### D-022 · 2026-08-29 · Принято
**Тёмная тема как единственная. Акцент — лайм `#D5FF40` вместо системного зелёного.**
Системный зелёный на чёрном читается как элемент операционной системы, а не как часть продукта. Светлой темы не делаем: поддерживать две вдвое дороже. Переменные заведены так, что светлую можно добавить позже без правки компонентов.

### D-023 · 2026-08-29 · Принято
**Фотографии блюд — первоклассная сущность, а не опциональное поле.**
Тёмный редакторский стиль держится на изображениях. Без них экран блюд — пустое чёрное поле. Библиотека готовых снимков лежит в `public/library`, сверху возможность загрузить своё.

### D-024 · 2026-08-29 · Принято
**Ползунок вместо галочки, пружинное движение, лаймовый кружок на оливковой дорожке.**
Дорожка во включённом состоянии не заливается лаймом целиком — светится только кружок. На списке из тридцати позиций это спокойнее.

### D-025 · 2026-08-29 · Принято
**Строки продуктов — плашки с изображением под информационным слоем.**
Зона снимка фиксирована по центру строки, поверх — градиент цвета плашки: края непрозрачные, к центру падает до 20%. Высота 56 с картинками, 48 без. Сорок не берём: минимальная зона касания 44.

### D-026 · 2026-08-29 · Принято
**Выбранная плитка блюда отмечается медалью на ленте.**
Лента чёрная с полупрозрачной лаймовой каймой, шириной с медаль, со скруглением снизу. Выезжает из-под верхнего края: лента первой, медаль догоняет с перелётом. Иконка — из макета Vadym, `#D5FF40`, галочка линией 2px с прямыми концами. Левый край медали, ленты и названия — на одной вертикали.

### D-027 · 2026-08-29 · Принято
**Названия блюд — антиквой. Только шрифты с кириллицей.**
Многие модные дисплейные гарнитуры идут только с латиницей. Проверять фильтром по кириллице до выбора. Взят Playfair Display.

### D-028 · 2026-08-29 · Принято
**План без даты и без слотов.**
Слоты «завтрак-обед-ужин» убраны: люди не планируют так. Дата убрана: планируют «на ближайшее время», а не на конкретный вторник. `meal_plans` → `planned_dishes`, уникальность по кухне, человеку и блюду.

### D-029 · 2026-08-29 · Принято
**Плитка и карусель — два вида одного выбора, не две сущности.**
Переключатель вида появляется только в режиме выбора. Библиотека и готовый список всегда плиткой.

### D-030 · 2026-08-29 · Принято
**Одна единица измерения на продукт, задаётся при создании. Ингредиент её наследует.**
Снимает проблему сложения разных единиц в общем списке. Черри в упаковках — отдельный продукт. Колонка `unit` из `dish_ingredients` удалена.

### D-031 · 2026-08-29 · Принято
**Количество у ингредиента — необязательное, но с первого дня.**
Первоначально хотели отложить как «трение ради цифры». Аргумент неверен: когда список общий, двое складывают потребность в один продукт, и без количества общий список хуже персонального. Не заполнено — показываем, для скольких блюд нужно.

### D-032 · 2026-08-29 · Принято
**Строки продуктов, нужных для плана, получают лаймовую грань слева 2px и подпись с блюдами.**
Плюс фильтр «Для плана». Своё блюдо — без подписи, чужое — с именем участника. Панель по тапу показывает количество и разбивку по блюдам.

### D-033 · 2026-08-29 · Принято
**Навигация двумя островками: вкладки и отдельно кнопка добавления.**
Разнесены, чтобы не промахиваться при частом переключении. Лайм отдан активной вкладке, кнопка добавления нейтральная: акцент должен принадлежать частому, а не редкому. Подпись показывается только у активной вкладки.

### D-034 · 2026-08-29 · Принято
**Мультиязычность заложена структурно, переводы отложены.**
Дешёвая часть — не хардкодить строки — делается сразу. Дорогая часть, сами переводы, откладывается. Отдельно исправлено то, что сидело в схеме: единицы измерения были русскими словами в CHECK-ограничении, категории и справочник продуктов лежали по-русски. Теперь всюду нейтральные ключи, подписи из словаря. Нормализация поиска — через Unicode-разложение, а не частный случай «ё→е».

### D-035 · 2026-08-29 · Принято
**Сетка 8 пикселей. Поиск от двух символов везде. Избранное личное.**
Личное избранное всегда сворачивается в общее (сколько человек отметили), обратно — нет. Это обратимый выбор.
