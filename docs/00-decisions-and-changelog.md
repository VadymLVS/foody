## Продукт и дистрибуция

### D-001 · 2026-07-28 · Принято
**Дистрибуция: сначала PWA, App Store — только после появления нативной ценности.**

Контекст: приложение в текущем виде — список, тогглы, модалки. Всё это работает в браузере.
App Store Guideline 4.2 отсеивает «переупакованные сайты»; отказ стоит не только времени, но и замедления всех последующих ревью.

Решение:
1. **Этап 1** — PWA на Vercel. Установка на домашний экран, share-ссылки для семьи.
2. **Этап 2** — упаковка в Capacitor, когда появится хотя бы одна функция, невозможная в браузере (сканирование чека камерой — главный кандидат).
3. Android/Google Play проще и может быть сделан раньше iOS.

Последствия: архитектура с первого дня пишется как Capacitor-ready. Все решения ниже вытекают из этого.

---

### D-002 · 2026-07-28 · Принято
**Отказ от Next.js Server Actions. Клиент ходит в Supabase напрямую.**

Контекст: внутри Capacitor фронтенд грузится с `capacitor://localhost` как статические файлы — Node-рантайма рядом нет, Server Actions не выполнятся.

Решение: весь доступ к данным — через `@supabase/supabase-js` с клиента. Защита — RLS в базе, а не серверный слой. Операции, которые клиент не может выполнить безопасно (вступление в кухню по коду, создание кухни, удаление аккаунта), выносятся в Postgres-функции `SECURITY DEFINER`.

Последствия: сборка одна и та же для веба и для нативной обёртки. Раздел «API / Server Actions» из старой спеки удалён целиком.

---

### D-003 · 2026-07-28 · Принято
**Стек: Vite + React + React Router. Next.js не используем.**

Контекст: после D-002 из Next.js не используется ничего — ни SSR, ни ISR, ни серверные метаданные. Остаётся только оверхед и конфликты с `output: 'export'`.

Решение: Vite 5 + React 18 + React Router v6. Быстрее сборка, проще Capacitor, меньше магии, статический вывод по умолчанию.

Последствия: одна и та же сборка едет на Vercel и в Capacitor. Никаких серверных маршрутов в проекте нет и не появится — если что-то нельзя сделать на клиенте, это Postgres-функция, а не эндпоинт.

---

### D-004 · 2026-07-28 · Принято (пересмотрено в тот же день)
**Swipe-режим выбора блюд входит в MVP-1 как основная функция.**

Контекст: изначальная мотивация продукта — облегчить ежедневный выбор «что есть». Учёт продуктов — фундамент, свайпы — то, ради чего всё затевалось. Первоначально был отложен в MVP-2; решение пересмотрено: без свайпов продукт неотличим от десятка списков покупок.

Решение: MVP-1 = продукты + блюда + **свайп-режим и план дня** + реалтайм + share. Таблица `meal_plans` активна с первого релиза. Спека режима — раздел 4 в `02-product-specification.md`.

Последствия:
- Порядок разработки: продукты → блюда → свайпы. Свайпы не могут работать без первых двух.
- Появляется третье измерение состояния — «сегодняшний план», он локален для пользователя, а не общий для кухни (см. D-019).
- Характер приложения (реакции на отказы) становится частью MVP и требует отдельного банка фраз.

---

### D-019 · 2026-07-28 · Принято
**План дня — персональный, не общий для кухни.**

Контекст: кухня общая, но «что я хочу съесть сегодня» — личное. Если план общий, два человека будут перетирать выбор друг друга.

Решение: `meal_plans` содержит `user_id`. Каждый свайпает своё. На экране плана видно, что выбрали остальные («Арина выбрала борщ») — но перезаписать чужой выбор нельзя.

Последствия: список покупок по плану собирается из объединения планов всех участников на дату.

---

### D-020 · 2026-07-28 · Принято
**Колода свайпов — не случайная. Приоритет: что можно приготовить прямо сейчас.**

Контекст: смысл продукта в том, чтобы не заставлять человека думать. Показывать блюдо, для которого нет половины ингредиентов, — это добавлять решение, а не убирать.

Решение: порядок колоды —
1. Блюда, готовые полностью (`missingCount = 0`) — перемешаны случайно;
2. Блюда, где не хватает 1–2 ингредиентов — с пометкой «нужно докупить: молоко»;
3. Остальные не показываются вообще.

Внутри первой группы — дополнительный сдвиг: блюда, которые давно не выбирались, идут раньше. Иначе колода вырождается в одни и те же три позиции.

---

### D-021 · 2026-07-28 · Принято
**Реакции на серию отказов — банк фраз, без повторов, с нарастанием.**

Контекст: задуманная «личность» приложения. Легко скатиться в раздражающее.

Решение: фразы показываются на 5-м, 10-м, 15-м и 20-м свайпе влево подряд. Тон нарастает от нейтрально-шутливого к абсурдному. Счётчик сбрасывается при любом свайпе вправо. Фраза не повторяется, пока не исчерпан весь банк. **Отключается в настройках** — не всем это смешно, и на третий день может раздражать.

## Данные и логика

### D-005 · 2026-07-28 · Принято
**Ингредиент блюда ссылается на `product_id` + хранит `product_name` как снапшот.**

Контекст: в старой спеке ингредиент — только строка. Переименовал «Молоко» → «Молоко 3.2%» — блюдо потеряло связь. Сравнение шло через `toLowerCase()`, то есть «Помидоры» ≠ «помидор».

Решение: `product_id uuid references products(id) on delete set null` + `product_name text not null` (снимок на момент добавления). Готовность блюда считается по `product_id`; `product_name` используется для отображения, если продукт удалён.

---

### D-006 · 2026-07-28 · Принято
**`in_stock` — единственный источник правды. `quantity` при выключении не сбрасывается.**

Контекст: старая спека сбрасывала количество в 0 при переключении в OFF. Случайный тап — и данные потеряны.

Решение: `quantity` сохраняется всегда. При `in_stock = false` количество просто не показывается в UI. Комбинация «в наличии, количество 0» допустима и означает «есть, сколько — не считали».

---

### D-007 · 2026-07-28 · Принято
**Сортировка списка: категория → название. Не алфавит по всему списку.**

Контекст: в старой спеке компаратор был сломан (второе сравнение недостижимо). Но главное — в магазине ходят по отделам, а не по алфавиту.

Решение: группировка по категориям со sticky-заголовками, внутри категории — алфавит. Порядок категорий фиксированный (Овощи → Фрукты → Молочка → Мясо → Бакалея → Заморозка → Напитки → Бытовое → Прочее), а не алфавитный.

---

### D-008 · 2026-07-28 · Принято
**Поиск: подстрока с приоритетом префикса, порог 2 символа, нормализация.**

Контекст: `startsWith` не находит «Хлеб бородинский» по запросу «бородин», а порог в 3 символа ломает поиск «яйцо» → «яй».

Решение: нормализация (lowercase, ё→е, схлопывание пробелов), фильтр `includes`, сортировка результатов: сначала совпадения с начала, потом остальные. Порог — 2 символа. Всё на клиенте (список продуктов кухни редко превышает 200 записей).

---

### D-009 · 2026-07-28 · Принято
**Удаление продукта — через toast «Отменить», без модалки подтверждения.**

Решение: продукт помечается `deleted_at` (soft delete), из UI исчезает мгновенно, 5 секунд висит toast с «Отменить». Физическое удаление — фоновой чисткой раз в 30 дней.
Модалка подтверждения остаётся только для необратимых действий: удаление кухни, удаление участника, удаление аккаунта.

---

### D-010 · 2026-07-28 · Принято
**Реалтайм: подавление собственного эха.**

Контекст: оптимистичное переключение тоггла + прилетевшее обратно собственное событие = мигание.

Решение: в `products` добавлено поле `updated_by`. Клиент игнорирует входящие события, где `updated_by = собственный user_id` **и** для этой записи есть незакрытая локальная операция. Плюс локальный `pendingOps: Map<id, {value, ts}>` с таймаутом 5 сек на случай потери ответа.

---

### D-011 · 2026-07-28 · Принято
**Инвайт-ссылка: срок жизни, отзыв, отдельный код для отзыва.**

Контекст: UUID не угадать перебором, но ссылка живёт вечно и утекает в семейных чатах, скриншотах, буфере обмена.

Решение: `invite_code` + `invite_expires_at` (по умолчанию +7 дней). Владелец может сгенерировать новую (старая мгновенно перестаёт работать) или отключить приглашения совсем. Вступление — только через RPC с проверкой срока.

## Интерфейс

### D-012 · 2026-07-28 · Принято
**Эмодзи убраны из интерфейса. Иконки — `lucide-react`.**

Контекст: 🛒🍽️⚙️✅❌ как элементы UI выглядят несерьёзно, по-разному рендерятся на платформах и не проходят по Apple HIG.
Решение: SVG-иконки, единый размер 20/24px, цвет через `currentColor`. Эмодзи допустимы только в текстах пустых состояний.

### D-013 · 2026-07-28 · Принято
**Голосовой ввод спрятан за абстракцией `VoiceInput`.**

Контекст: Apple не включила Web Speech API в WKWebView, при этом `webkitSpeechRecognition` в `window` присутствует — проверка на существование даёт ложноположительный результат, распознавание молча не работает.
Решение: интерфейс с двумя реализациями — Web Speech API (браузер) и `@capacitor-community/speech-recognition` (нативная сборка). Определение платформы, а не feature-detection. Кнопка микрофона скрывается, если ни одна реализация недоступна.

### D-014 · 2026-07-28 · Принято
**Тач-таргеты минимум 44×44px, safe-area insets с первого дня.**
Иконка «⋮» в карточке — визуально 20px, кликабельная зона 44px. Нижняя навигация — `padding-bottom: env(safe-area-inset-bottom)`.

## Безопасность

### D-015 · 2026-07-28 · Принято
**RLS через `SECURITY DEFINER`-функцию `is_kitchen_member()`.**

Контекст: политика на `kitchen_members`, которая проверяет членство через саму `kitchen_members`, вызывает бесконечную рекурсию в Postgres — классическая ошибка Supabase-проектов.
Решение: вспомогательная функция `is_kitchen_member(uuid)` с `security definer` и зафиксированным `search_path`. Все политики ссылаются на неё.

### D-016 · 2026-07-28 · Принято
**Каждая политика имеет и `using`, и `with check`.**

Контекст: в старой спеке `for all using (...)` без `with check` — любой авторизованный пользователь мог вставить строку в чужую кухню.
Решение: политики разделены по операциям (`select` / `insert` / `update` / `delete`), у пишущих обязателен `with check`. Проверка внесена в чеклист ревью.

### D-017 · 2026-07-28 · Принято
**Фото блюд: приватный бакет, EXIF стрипается на клиенте.**
Фотография кухни содержит GPS-координаты дома. Перед загрузкой изображение перерисовывается через canvas — метаданные теряются, заодно сжимается размер. Бакет не публичный, доступ — по подписанным URL, политики на `storage.objects` по `kitchen_id` в пути.

### D-018 · 2026-07-28 · Принято
**Удаление аккаунта — обязательная функция с первого релиза.**
App Store Guideline 5.1.1(v) требует удаление аккаунта внутри приложения. Реализуется как RPC с передачей владения кухнями или их удалением. Делаем сразу, чтобы не встраивать задним числом.

## Визуальный язык и модель (сессия 2)

### D-022 · 2026-08-29 · Принято
**Тёмная тема как единственная. Акцент — лайм `#D5FF40` вместо системного зелёного.**
Системный зелёный на чёрном читается как элемент операционной системы, а не как часть продукта. Светлой темы не делаем: поддерживать две вдвое дороже. Переменные заведены так, что светлую можно добавить позже без правки компонентов.

### D-023 · 2026-08-29 · Принято
**Фотографии блюд — первоклассная сущность, а не опциональное поле.**
Тёмный редакторский стиль держится на изображениях. Без них экран блюд — пустое чёрное поле. Библиотека готовых снимков лежит в `public/library`, сверху возможность загрузить своё.

### D-024 · 2026-08-29 · Принято
**Ползунок вместо галочки, пружинное движение, лаймовый кружок на оливковой дорожке.**
Дорожка во включённом состоянии не заливается лаймом целиком — светится только кружок. На списке из тридцати позиций это спокойнее.

### D-025 · 2026-08-29 · Принято
**Строки продуктов — плашки с изображением под информационным слоем.**
Зона снимка фиксирована по центру строки, поверх — градиент цвета плашки: края непрозрачные, к центру падает до 20%. Высота 56 с картинками, 48 без. Сорок не берём: минимальная зона касания 44.

### D-026 · 2026-08-29 · Принято
**Выбранная плитка блюда отмечается медалью на ленте.**
Лента чёрная с полупрозрачной лаймовой каймой, шириной с медаль, со скруглением снизу. Выезжает из-под верхнего края: лента первой, медаль догоняет с перелётом. Иконка — из макета Vadym, `#D5FF40`, галочка линией 2px с прямыми концами. Левый край медали, ленты и названия — на одной вертикали.

### D-027 · 2026-08-29 · Принято
**Названия блюд — антиквой. Только шрифты с кириллицей.**
Многие модные дисплейные гарнитуры идут только с латиницей. Проверять фильтром по кириллице до выбора. Взят Playfair Display.

### D-028 · 2026-08-29 · Принято
**План без даты и без слотов.**
Слоты «завтрак-обед-ужин» убраны: люди не планируют так. Дата убрана: планируют «на ближайшее время», а не на конкретный вторник. `meal_plans` → `planned_dishes`, уникальность по кухне, человеку и блюду.

### D-029 · 2026-08-29 · Принято
**Плитка и карусель — два вида одного выбора, не две сущности.**
Переключатель вида появляется только в режиме выбора. Библиотека и готовый список всегда плиткой.

### D-030 · 2026-08-29 · Принято
**Одна единица измерения на продукт, задаётся при создании. Ингредиент её наследует.**
Снимает проблему сложения разных единиц в общем списке. Черри в упаковках — отдельный продукт. Колонка `unit` из `dish_ingredients` удалена.

### D-031 · 2026-08-29 · Принято
**Количество у ингредиента — необязательное, но с первого дня.**
Первоначально хотели отложить как «трение ради цифры». Аргумент неверен: когда список общий, двое складывают потребность в один продукт, и без количества общий список хуже персонального. Не заполнено — показываем, для скольких блюд нужно.

### D-032 · 2026-08-29 · Принято
**Строки продуктов, нужных для плана, получают лаймовую грань слева 2px и подпись с блюдами.**
Плюс фильтр «Для плана». Своё блюдо — без подписи, чужое — с именем участника. Панель по тапу показывает количество и разбивку по блюдам.

### D-033 · 2026-08-29 · Принято
**Навигация двумя островками: вкладки и отдельно кнопка добавления.**
Разнесены, чтобы не промахиваться при частом переключении. Лайм отдан активной вкладке, кнопка добавления нейтральная: акцент должен принадлежать частому, а не редкому. Подпись показывается только у активной вкладки.

### D-034 · 2026-08-29 · Принято
**Мультиязычность заложена структурно, переводы отложены.**
Дешёвая часть — не хардкодить строки — делается сразу. Дорогая часть, сами переводы, откладывается. Отдельно исправлено то, что сидело в схеме: единицы измерения были русскими словами в CHECK-ограничении, категории и справочник продуктов лежали по-русски. Теперь всюду нейтральные ключи, подписи из словаря. Нормализация поиска — через Unicode-разложение, а не частный случай «ё→е».

### D-035 · 2026-08-29 · Принято
**Сетка 8 пикселей. Поиск от двух символов везде. Избранное личное.**
Личное избранное всегда сворачивается в общее (сколько человек отметили), обратно — нет. Это обратимый выбор.

### D-036 · 2026-09-16 · Принято
**Импорт чека: загрузка готового снимка, разбор мультимодальной моделью, обязательная проверка.**
Съёмка в приложении не нужна — системный выбор файла и так предлагает камеру, а без неё открывается сценарий «сфотографировал в магазине, разобрал дома». Распознавание текста на устройстве отвергнуто: магазинные сокращения вроде `L.DESN.S/L.ASTUR.1L` оно не расшифрует, попаданий было бы около трети, и инструментом бы не пользовались. Ключ модели живёт в Edge Function: всё, что попадает в сборку, видно любому. Ничего не применяется автоматически — экран разбора обязателен. Сопоставление идёт с продуктами кухни, а не только со справочником, иначе «Черри» заведёт дубль. Снимок не сохраняется.

### D-037 · 2026-09-16 · Принято
**Очередь несохранённых изменений вместо отката.**
Главный сценарий — подвал супермаркета, где связь пропадает. Раньше не долетевшее изменение откатывалось: отметил десять позиций, сохранилось три. Теперь сетевая ошибка ставит операцию в очередь и сохраняет локальное значение; несетевые ошибки по-прежнему откатываются, потому что повтор их не спасёт. Код отдаёт `kitchen_invite(p_kitchen)` — владельцу и по одной кухне; менять его по-прежнему можно только через `regenerate_invite`. Переименование кухни остаётся у любого участника: кухня общая, и кнопка «Переименовать» видна всем.

### D-067 · 2026-09-29 · Принято
**Блюдо попадает в меню только со своей кухни — два рубежа.**
Политика `planned_insert` проверяла членство в кухне из самой строки, но не сверяла с ней `dish_id`: подставив чужой `dish_id` со своей кухней, человек видел чужой продукт в «Купить» через `plan_needs` (проверено, «Секретный продукт · 3.00»). Теперь политика сверяет кухню блюда, а триггер `guard_planned_kitchen` закрывает тот же путь для функций, которые идут в обход RLS (`apply_dish_set`).

### D-068 · 2026-09-29 · Принято
**Количество в списке покупок считается по блюдам, а не по выборам.**
`plan_needs` складывал строки на каждую пару «выбор человека × ингредиент»: одно блюдо, выбранное двумя, просило 1 кг вместо 0,5 при `dish_count = 1`. Теперь блюдо участвует в подсчёте один раз, а подпись «чьё» собирается отдельно: если блюдо выбрал и ты — подписи нет, если только другой человек — его имя. Заодно блюда и продукты в функции берутся только из запрошенной кухни.

### D-069 · 2026-09-29 · Принято
**Почту соседей по кухне база больше не отдаёт.**
Политика `profiles_select_cokitchen` отдавала участникам весь профиль друг друга: по утёкшей ссылке-приглашению можно было собрать адреса. Профиль читает только сам человек, а список участников отдаёт `kitchen_people(p_kitchen)` — имя, аватар, роль и почту только свою. На экране кухни вместо чужой почты показывается роль.

### D-070 · 2026-09-29 · Принято

### D-071 · 2026-09-29 · Принято

### D-073 · 2026-09-29 · Принято
**Очередь правок не теряет отметку, сделанную во время отправки, и говорит о неудаче.**
Из очереди операция убиралась по одному ключу: если во время отправки человек отметил тот же продукт ещё раз, новая отметка исчезала вместе с отправленной. Отказ сервера по-прежнему отбрасывается без повтора, но теперь об этом говорит тост: в списке отметка уже стоит, и молчать нельзя.

### D-074 · 2026-09-29 · Принято
**Кэш service worker чистится при смене аккаунта.**
`resetAccountState` чистил кэш запросов, но не кэш ответов Supabase, который service worker держит по `NetworkFirst` и который переживает выход и закрытие приложения: без сети новый аккаунт увидел бы оттуда чужие продукты. Теперь кэши с «api» в имени удаляются при выходе, входе и любой смене пользователя.

### D-075 · 2026-09-29 · Принято
**Выключенный продукт не держит прежнее количество; у сброса есть отмена.**
Количество у выключенной позиции быстро становится неактуальным: в магазине человек смотрит «сколько брать» и видит цифру с прошлого раза (Vadym, 09-26). Выключение ползунка сбрасывает количество в ноль. Это возвращает D-006, отменённый в v0.2, и по той же причине, по которой его отменяли (потеря данных от одного касания) рядом стоит «Отменить» — тост с ключом, поэтому подряд выключенные позиции собираются в один тост и возвращаются все разом, а не только последняя.

### D-076 · 2026-09-29 · Принято
**«Выключить всё» — в меню «Ещё», с числом, областью и снимком для возврата.**
Отдельного экрана «актуализировать список» не будет (решение Vadym): кнопка живёт в меню «⋯» рядом с импортом чека. Область — то, что человек видит: отдел при выбранной вкладке, найденное при поиске, иначе вся кухня; число и область стоят прямо в подтверждении («Выключить 11 продуктов во всей кухне?»). Количества сбрасываются вместе с наличием, снимок для «Отменить» держится до следующего действия, а не пять секунд: человек уходит проходить список и возвращается не сразу.

### D-077 · 2026-09-29 · Принято
**Подсказки выбираются на отпускании касания.**
Выбор висел на `onClick`, и с открытой клавиатурой он не срабатывал: на iPhone касание вне поля сначала снимает фокус, клавиатура уезжает, страница пересчитывает высоту — и к моменту `click` под пальцем уже другой элемент (Vadym, 09-26). Теперь решение принимается на `touchend`, там же `preventDefault()` (он отменяет и эмулированный `click`, так что дважды не срабатывает). `touchstart` не отменяем — иначе список подсказок перестал бы прокручиваться пальцем, начатым со строки. Сдвиг больше 10 px считается прокруткой. Мышь и клавиатура идут прежним путём. Мест было больше, чем в жалобе: состав блюда и набора, форма продукта, «Создать «X»» под поиском.

### D-078 · 2026-09-29 · Принято
**Необратимое действие либо спрашивает, либо даёт «Отменить».**
Удаление блюда мягкое — значит, у него есть «Отменить» (как у продуктов, D-009); для этого появился `restoreDish`. Удаление набора спрашивает вторым шагом в том же окне, без вложенного модала. У готового набора это «больше не предлагать», поэтому подпись «Скрыть», а не «Удалить». Удаление человека из кухни спрашивает и говорит, что он потеряет и как вернётся. «Очистить меню» показывает в подтверждении, сколько блюд и наборов уйдёт.

### D-079 · 2026-09-29 · Принято
**Карточка блюда не «добавляет недостающее», а отмечает наличие.**
Кнопка и «+» у ингредиента ставили `in_stock = true`, то есть убирали продукт из «Купить» — ровно наоборот подписи «Добавить недостающее». Добавлять в покупки и не нужно: продукт без наличия и так в «Купить», а с блюдом в меню приходит туда с количеством. Теперь подпись «Отметить, что всё есть», у ингредиента вместо «+» слово «есть», у обоих — тост с «Отменить».

### D-080 · 2026-09-29 · Принято
**Новая версия доезжает до телефона сама и видна в Настройках.**
Приложение не подключало `virtual:pwa-register`: браузер брал прежнюю сборку из кэша, и жалобы «у меня старая версия» объяснялись этим (обзор 09-26, R-10). Теперь при готовности новой сборки приходит тост «Обновить» — молча подменять экран под руками нельзя, человек может стоять в магазине с открытым списком. При возврате в приложение и при появлении сети обновление проверяется само. Если приложение только что открыли и в очереди нет неотправленных правок, новая версия ставится сразу и молча: спрашивать на пустом экране незачем. Внизу Настроек — версия сборки и дата.

### D-081 · 2026-09-29 · Принято
**Подписи светлее, мелкие кнопки прежнего вида с невидимой зоной 44 px.**
`--text-muted` #6E6E6E давал контраст 4.1:1, `--text-dim` #5C5C5C — 3.1:1, при норме 4.5:1, а этим набраны все подсказки, единицы и неактивные вкладки (обзор 09-26, U-4). Стало #8A8A8A и #7A7A7A — выбор Vadym по макету «до/после». ### D-082 · 2026-09-29 · Принято (уточняет D-064)

### D-083 · 2026-09-30 · Принято
**«Выключить всё» стоит над списком, а не в меню «⋯».**
Кнопку положили в меню «⋯» в шапке как редкое действие, но «актуализировать список» — часть обычного похода в магазин, не реже смены фильтра. Плюс нажатие в правом верхнем углу открывало лист снизу: связи между нажатием и результатом не видно (замечание Vadym 09-30). ### D-084 · 2026-09-30 · Принято
**Список покупок — это фильтр, а не действие.**
Все пути к покупкам шли через блюда: карусель, наборы, «Для меню» — то есть отвечали на вопрос «что готовим». Вопроса «что я обычно покупаю» в приложении не было, и перед магазином человек открывал «Купить» на всю кухню (замечание Vadym 09-30). Появились списки: выбор списка ничего не меняет в продуктах, он сужает выдачу и показывает свои позиции как есть — и те, что есть дома, и те, которых нет. Это принципиально отличает их от наборов блюд (D-053), которые при применении переписывают наличие и складывают количества; поэтому отдельные таблицы `product_lists` и `product_list_items`, а не переиспользование `dish_sets`. Количества у позиции нет: количество живёт у продукта (D-030), второе рядом сразу начало бы расходиться с первым. Внутри выбранного списка фильтры состояния не применяются — иначе отмеченное исчезало бы из-под пальца.

### D-085 · 2026-09-30 · Принято
**Выбор списка — пилюля со стрелкой в том же ряду; сам выбор открывается снизу.**
Vadym описал табу с названием выбранного списка и стрелкой вниз. Пилюля стоит в конце ряда фильтров, при активном списке подсвечена и показывает его название (длинное обрезается, стрелка видна всегда), а ряд сам подводится к ней. Панель выбора — лист снизу, а не выпадающий список у верхнего края: большим пальцем до верха не дотянуться, и все остальные меню приложения открываются так же. В панели — «Все продукты» (выход), списки с числом позиций, «Изменить» для выбранного и «Создать список». Отдельного экрана управления списками нет: восьми позиций в листе достаточно, а лишний экран в уже сложной структуре только мешает.

### D-086 · 2026-09-30 · Принято
**Разовый список «купить сейчас» всплывает сам и закрывается вручную.**
Второй вид списка — на одну поездку: его создаёт один человек для другого, который уже в магазине. Он приходит через realtime (без перезапуска), показывается яркой полосой над поиском и один раз за запуск приложения открывается сам — искать его в структуре не нужно. Отметка о показе живёт в `sessionStorage`: вышел из списка сам — в этот раз больше не навязываемся; открыл приложение у полки заново — список снова первым, пока поездка не закрыта. Полоса остаётся видна всегда и возвращает к списку одним нажатием. Закрывает список любой участник — создаёт один, а возвращается из магазина другой; закрытый уходит из выдачи, но остаётся в базе историей. Когда отмечена последняя позиция, приходит тост «Всё куплено · Закрыть список» — тостом, а не окном: закрывать необязательно, и перегораживать экран вопросом незачем.

### D-087 · 2026-09-30 · Принято
**Состав списка собирается поиском или целиком из «Купить».**
Набрать двадцать позиций поиском по одной никто не будет, а собирают список чаще всего стоя над фильтром «Купить». Поэтому в форме есть и поиск продукта (тот же `ProductPicker`, что у блюд и наборов), и кнопка «Взять из «Купить»», которая добавляет всё некупленное разом. Удаление списка спрашивает подтверждение в том же окне, без вложенного модала (как у наборов, D-078).

### D-088 · 2026-09-30 · Принято (уточняет D-083)
**Закреплённая кнопка стоит рядом с полосой прокрутки, а не поверх неё.**
Сначала «Очистить список» лежало поверх ряда фильтров, а место под него резервировалось отступом внутри самой полосы. Из-за этого ряд «прокручивался» ровно на ширину отступа: на телефоне палец тянул его почти вхолостую, а первая пилюля уезжала за левый край (замечание Vadym 09-30). Заодно убрана безусловная прокрутка ряда к пилюле выбранного списка — теперь она случается только если пилюля действительно не видна целиком.

### D-089 · 2026-09-30 · Принято (уточняет U-6)
**Поля ввода набираются 16 px.**
В v0.16 убран `maximum-scale=1`, потому что он запрещал увеличение текста жестом. Обратная сторона: iOS увеличивает страницу при фокусе, если у поля кегль меньше 16 px, и после ввода масштаб приходится разводить руками — так и случилось на форме списка и на поиске продукта (замечание Vadym 09-30). Возвращать `maximum-scale` нельзя: это ломает доступность. Поэтому у полей ввода, текстовых областей и полноразмерных списков выбора свой токен `text-field` = 16 px. Компактный выбор единицы в строке состава пока 12 px — его надо проверить на телефоне отдельно.

### D-090 · 2026-09-30 · Принято (уточняет D-076)
**Действие называется «Очистить список», значок — ластик.**
«Выключить всё» в шапке продуктов читалось странно: человек не выключает, а отмечает, что ничего нет, чтобы пройтись по списку заново (замечание Vadym 09-30). ### D-091 · 2026-09-30 · Принято (уточняет D-085, D-087)

Справочник по-прежнему целиком в коде: блюда, названия, рецепты, единицы и группы питания продуктов. Миграция не нужна. 22 новых продукта (шпинат, батат, мидии, тофу, слоёное тесто…) заводятся в кухне блюдом с отделом и единицей; единицы уже существующих продуктов взяты из сида, чтобы не расходиться с тем, что в кухне уже есть. Новые группы питания: треска и хек — рыба, мидии — морепродукты, рикотта — молочное, песто — молочное и орехи, тортильи — глютен, слоёное тесто — глютен и молочное.

Справочник живёт в четырёх местах сразу, и пропуск в любом ломается тихо: блюдо показывается ключом, приходит без рецепта или создаёт продукт без отдела. Поэтому `dishLibrary.test.ts` проверяет целостность — названия, рецепты, единицы, категории, наборы — и сам потолок мясных блюд.

### D-105 · 2026-10-04 · Принято
**Регистрация различает «вошёл» и «письмо отправлено».**
`signUp` разбирал только ошибку. При включённом в Supabase подтверждении почты сессии после регистрации нет, ошибки тоже нет — и код шёл на `/products`, роутер видел пустую сессию и возвращал на приветственный экран. Человек заполнял форму, нажимал «Продолжить» и оказывался там же, без слова о письме (п. 53, найдено при чтении кода, когда Vadym дал приложение тестеру). Сейчас подтверждение у Vadym выключено (по данным Authentication → Users), но пробел сломал бы регистрацию молча в тот день, когда его включат.

Теперь `signUp` возвращает `needsConfirmation`, и экран показывает «Проверьте почту» с адресом, подсказкой про «Спам», повтором письма через минуту (встроенная почта Supabase отдаёт единицы писем в час) и «Уже подтвердил — войти». Код приглашения при этом не сбрасывается: после перехода по ссылке роутер сам отправит человека в нужную кухню (п. 31).

Ссылка из письма ведёт туда, откуда человек регистрировался (`emailRedirectTo: window.location.origin`), а не на Site URL проекта: если там остался адрес разработки, человек подтвердил бы почту и оказался в никуда. Адрес должен быть в Redirect URLs проекта — иначе Supabase сам откатится к Site URL.

### D-106 · 2026-10-04 · Принято (уточняет D-043, D-104)
**Блюда — витрина всего справочника, а не только заведённого в кухне.**
Vadym: «Хочу сейчас увидеть весь список блюд, чтобы быстро выбрать что хочу на неделе, а единственный способ увидеть все, это играться с этой каруселью. Это ведь делался способ выбирать, когда не знаешь чего хочешь, а список плитками — это как раз когда выбираешь чего хочешь… нужно во всех блюдах отображать все сразу, что есть в базе, только исключая диету, „в меню“ уже отобразить то, что было выбрано».

Причина — в D-043: справочник задумывался как источник для первого наполнения пустой кухни, поэтому был виден только через карусель. После расширения до 113 блюд (D-104) это стало тупиком: выбрать конкретное можно было только пролистав колоду.

Теперь вкладка «Все» показывает каталог: блюда кухни и весь справочник, подходящий по питанию (`buildCatalog`, с модульными тестами). Решения внутри, мои — Vadym задал цель, а не устройство:
- **Блюдо справочника в базу не пишется, пока его не выбрали.** До этого оно «виртуальное» (`lib:<ключ>`), и 83 невыбранных блюда кухню не захламляют. Выбор заводит блюдо и недостающие продукты и сразу ставит в меню.
- **Порядок — по алфавиту, общий.** При выборе блюдо из виртуального становится настоящим; если бы блюда кухни шли первыми, плитка перескакивала бы через всю сетку — п. 17.
- **Питание отсекает только справочник.** Блюда кухни видны всегда: кухня общая, чужое не прячется (D-060).
- **«Добавить в меню» — прямо в карточке блюда**, для любого блюда не из меню. Раньше для этого надо было выйти в режим «Составить меню». У блюда справочника в карточке нет правки, избранного и удаления — в кухне его ещё нет.
- **Шага «что из этого уже есть дома?» при выборе из каталога нет.** Он прерывал бы составление меню на каждом блюде. Новые продукты заводятся «нет дома» — выбранное блюдо повод купить; наличие отмечается в карточке или в «Купить».
- **Нажатия выстраиваются в очередь**: два блюда с общим продуктом, выбранные подряд, иначе завели бы продукт дважды. Плитка отмечается медалью сразу, не дожидаясь сети.
- **«Отмена» в режиме выбора убирает блюда справочника вместе с продуктами**, которые они завели, — и дожидается тех, что ещё заводятся. Пока идёт уборка, кнопка показывает загрузку, и счётчик «В меню» не скачет. Эту поломку нашёл прежний набор сценариев: «Отмена» оставляла выбранное в меню, а продукты — в «Купить».

Карусель осталась в «+» — для «не знаю, чего хочу».
